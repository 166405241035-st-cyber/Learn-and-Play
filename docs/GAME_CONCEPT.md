# Learn-and-Play — คอนเซ็ปหลักฉบับเริ่มใหม่

ฉบับ 1.1 · 9 ตุลาคม 2026 (Asia/Bangkok)

**สถานะ: สรุปทิศทางที่ผู้ใช้ยอมรับและข้อเสนอสำหรับออกแบบต่อ ยังไม่มีระบบเกมฉบับใหม่**

ผู้ใช้ขอเริ่มออกแบบใหม่หลังทดลองต้นแบบแล้วพบว่า GUI และการเล่นเข้าใจยาก บทสอนมุมจอไม่ช่วย และการหมุนกล้องเพิ่มงาน จากนั้นเสนอคอนเซ็ปหมู่บ้านกับร้านที่เข้าผ่านแผนที่ และสั่งล้างโค้ด/เอกสารเก่า เอกสารนี้เป็นฐานหลักใหม่ ไม่สืบทอดตัวเลข เงื่อนไขผ่าน หรือผังของต้นแบบเดิมโดยอัตโนมัติ

## 1. แกนเกม

ผู้เล่นเป็นผู้ดูแลหมู่บ้าน มีพื้นที่ให้คนเข้ามาอยู่อาศัยหรือเปิดกิจการ เลือกรับคำขอ จัดสรรแปลง และช่วยออกแบบพื้นที่/กิจการเพื่อให้ชุมชนเติบโต

คณิตศาสตร์เป็นเครื่องมือในการตัดสินใจและแก้ปัญหา เช่น พื้นที่เช่า วัสดุ งบ จำนวนสินค้า ราคา และการอ่านผลกิจการ ผู้เล่นต้องเห็นว่าคำนวณสิ่งนั้นไปทำไม แล้วเห็นผลของแผนในโลก

ยังรักษาเป้าหมาย Sandbox: เลือกงาน เลือกทางออก ทดลอง แก้แผน และออกแบบผลงานเอง มีการสอนตรง ๆ การประเมินจากหลักฐาน และพอร์ตเตรียมเป็นระบบภายหลัง วิชาอื่นเตรียมจุดเชื่อมโดยยังไม่ผลิตหลักสูตรของวิชาเหล่านั้น

## 2. สิ่งที่ตกลงแล้วกับสิ่งที่ยังต้องออกแบบ

| สถานะ | รายการ |
| --- | --- |
| ยืนยันจากผู้ใช้ | ร้านเข้าจากแผนที่: กดสถานที่ → เปลี่ยนฉาก → หน้าร้าน มีภาพ NPC และฉากหลังร้านนั้น |
| ยืนยันจากผู้ใช้ | จัดสรรพื้นที่โดยตรง ไม่มีตัวละครผู้เล่นเดิน มีคำขอของ NPC |
| ยืนยันจากผู้ใช้ | ผู้เล่นเลือกว่าจะรับเข้าหมู่บ้านหรือไม่ และช่วยแก้ปัญหา/ออกแบบให้หมู่บ้านพัฒนา |
| ยืนยันจากผู้ใช้ | ตัดการหมุนกล้อง; กล้องหมู่บ้านใช้มุมเดียว |
| ฐานที่เสนอและผู้ใช้ตอบตกลง | หมู่บ้านมีแปลงว่างให้ NPC เช่า ผู้เล่นช่วยจัดสรร ไม่ใช่ผู้เล่นเช่าที่เพื่อปล่อยต่อ |
| ข้อเสนอสำหรับต้นแบบใหม่ | เริ่มงานบ้านและร้านขายของชำก่อน ร้านอาหารเป็นงานต่อยอด |
| ยังไม่ตกลงรายละเอียด | ขนาดแผนที่/แปลง ค่าเช่า งบ รอบเวลา ต้นทุนก่อสร้าง รายได้หมู่บ้าน และความหมายของความรุ่งเรือง |
| ยังต้องออกแบบ | วงจรคำขอ หน้าต่างคุย ผังวางแผน การเรียนตรงจุด การซื้อ/คืน การจัดสินค้า และการทดลองกิจการ |
| ยังไม่มี | โค้ดฉบับใหม่ ภาพที่รับรองตรงแบบใหม่ การประเมิน/พอร์ต/เซฟฉบับใหม่ |

คำว่า “ซื้อที่” ในแนวคิดแรกปรับเป็นเช่าแปลงตามข้อเสนอที่ผู้ใช้ยอมรับ รายละเอียดผู้จ่าย ผู้รับ ระยะเช่า และการยกเลิกยังไม่กำหนด การซื้อขาดไม่ใส่ในงานชุดแรกโดยอัตโนมัติ

## 3. พื้นที่เกมสองชนิด

### 3.1 หมู่บ้านสำหรับจัดสรรพื้นที่โดยตรง

ผู้เล่นเลือกแปลงและคำขอผ่านหน้าจอ ไม่มีตัวละครผู้เล่นเดิน ไม่มีระบบเดินหลบสิ่งก่อสร้างหรือกล้องตามตัวละคร การอ่านผังและผลการจัดสรรต้องชัดเจน รายละเอียด GUI ออกแบบหลังฐานการเรียนรู้

### 3.2 สถานที่เข้าผ่านแผนที่

เปิดแผนที่ → เลือกสถานที่ เช่นร้านวัสดุ → แสดงการเปลี่ยนฉาก/โหลดตามจริง → หน้าร้านที่มี NPC และฉากหลังเฉพาะร้าน → ซื้อหรือคุย → กลับหมู่บ้าน

หน้าร้านแสดงข้อมูลที่จำเป็นต่อร้านนั้น: สินค้า หน่วย ราคา จำนวนที่เลือก เงิน และรายการก่อนยืนยัน ไม่บังคับเดินหาตำแหน่งร้านในฉากหมู่บ้านก่อนซื้อ ไม่มีเหตุผลต้องหน่วงเวลาโหลดปลอม; ข้อมูลรายการและตำแหน่งกลับต้องไม่สูญหายเมื่อเปลี่ยนฉาก

ร้านที่เข้าจากแผนที่เป็นสถานที่ผู้เล่นไปซื้อของ ส่วนร้านที่ผู้เล่นช่วย NPC เปิดเป็นกิจการในหมู่บ้าน ต้องแยกหน้าที่ทั้งสองอย่างให้ผู้เล่นเข้าใจ

## 4. วงจรการเล่นหลัก

| ช่วง | สิ่งที่ผู้เล่นทำ | ผลที่เห็น/ข้อมูลที่ต้องมี |
| --- | --- | --- |
| 1 รับคำขอ | คุยกับคนที่อยากอยู่หรือเปิดกิจการ | ความต้องการ งบ ข้อจำกัด และสิ่งที่ยังไม่ทราบ |
| 2 สำรวจ | ดูแปลง ทางเข้าถึง และข้อมูลพื้นที่ | ขนาด หน่วย เงื่อนไขแปลง ไม่วัดจากภาพเอียง |
| 3 เสนอทางเลือก | รับเข้า เสนอแปลง/ขนาดอื่น ขอข้อมูลเพิ่ม หรือพักคำขอ | เหตุผลและแผนที่ชาวบ้านพิจารณา |
| 4 ออกแบบ | วางผัง คิดพื้นที่ วัสดุ งบ หรือรายการสินค้า | แผนที่แก้และเปรียบเทียบได้ |
| 5 ซื้อ/ลงมือ | เข้าร้านจากแผนที่ แล้วกลับมาจัดพื้นที่ | รายการซื้อ ของที่ได้รับ และผลในโลก |
| 6 ทดลองและแก้ | ดูการใช้งานหรือปัญหากิจการ | ปัญหาที่อธิบายได้และทางแก้หลายแบบ |
| 7 เห็นพัฒนา | คน/อาคาร/บริการใหม่เกิดขึ้น | ความเปลี่ยนแปลงชุมชนและฉบับผลงานที่เก็บได้ |

ลำดับนี้เป็นเส้นทางแนะนำ ไม่บังคับผู้เล่นย้อนแก้ไม่ได้ ผู้เล่นพักคำขอ เปิดบทเรียน หรือปรับแผนก่อนยืนยันได้ การเปลี่ยนแผนหลังซื้อหรือเริ่มก่อสร้างต้องมีกติกาทรัพยากรที่ชัดก่อนเขียนระบบ

การรับ/ไม่รับคนเป็นการเลือกจัดการหมู่บ้าน ไม่ใช่คำตอบคณิตศาสตร์ที่ถูกเพียงทางเดียว ไม่กำหนดคุณค่าของคนจากความร่ำรวยหรือคะแนนผู้เล่น

## 5. ประเภทโครงการที่เสนอ

### บ้าน — เสนอเป็นงานเริ่มต้น

คนอยากย้ายมาอยู่ แจ้งจำนวนคนและความต้องการพื้นที่ ผู้เล่นช่วยเลือกแปลง วางส่วนใช้งาน เตรียมวัสดุ และตรวจงบ

คณิตศาสตร์ที่อาจเกี่ยว: หน่วย พื้นที่ สัดส่วน ร้อยละและงบ ต้องกำหนดข้อมูลครบและออกแบบบทก่อนใช้จริง ไม่แสดงว่าความต้องการอยู่อาศัยในเกมเป็นมาตรฐานบ้านจริง

### ร้านขายของชำ — เสนอเป็นงานเริ่มต้นถัดมา

คนอยากเปิดร้าน ผู้เล่นช่วยพื้นที่ขาย/เก็บสินค้า ตำแหน่งชั้น และสินค้าเริ่มต้น

เริ่ม “ออกแบบสินค้า” จากเลือกชนิด จำนวน ต้นทุน/ราคาขาย และการจัดวางตามข้อมูลโจทย์ ไม่เพิ่มระบบประดิษฐ์ผลิตภัณฑ์อิสระทันที คณิตศาสตร์อาจเกี่ยวจำนวน ต้นทุน กำไร อัตราส่วนและข้อมูลยอดขาย

ต้องกำหนดที่มาของข้อมูลความต้องการและการซื้อของชาวบ้านก่อนจำลองผลกิจการ ไม่ใช้ยอดขายสุ่มเพียงอย่างเดียวตัดสินความรู้

### ร้านอาหารเล็ก — ข้อเสนอระยะต่อยอด

พื้นที่เตรียม/เสิร์ฟ เมนู วัตถุดิบ และต้นทุน เหมาะเชื่อมอัตราส่วนและข้อมูลกิจการ แต่ไม่รวมในต้นแบบแรกจนงานบ้าน/ของชำเข้าใจง่ายแล้ว

ประเภทอื่น เช่นสวนหรือกิจการบริการ คุยเพิ่มภายหลัง ไม่ถือว่าทุกประเภทได้รับอนุมัติแล้ว

## 6. ตัวอย่างสถานการณ์ — ยังไม่ใช่โจทย์พร้อมเล่น

NPC บอกว่า “อยากเปิดร้านขายของชำเล็ก ๆ มีงบจำกัด ต้องมีพื้นที่ขายและเก็บสินค้า ช่วยหาที่ให้หน่อย”

ผู้เล่นขอรายละเอียด ดูแปลง เปรียบเทียบพื้นที่/ค่าเช่า เสนอแผน แล้วจัดชั้นกับรายการสินค้า หากพื้นที่เก็บไม่พอหรือเกินงบ ต้องมองเห็นสาเหตุและทางเลือก เช่นย้ายของ ลดรายการ หรือเสนอแปลงอื่น

ยังไม่กำหนดตัวเลขเพราะต้องออกแบบแปลงและเศรษฐกิจก่อน ไม่ยกพื้นที่4×6/งบ4,000/วัสดุA/Bเดิมเป็นกติกาใหม่โดยอัตโนมัติ

## 7. ความรุ่งเรืองของหมู่บ้าน

เริ่มจากสิ่งที่มองเห็น: คนมาอยู่ อาคารถูกใช้งาน มีร้าน/บริการที่เคยขาด แปลงว่างกลายเป็นพื้นที่มีประโยชน์ และปัญหาที่แก้แล้ว

ตัวชี้วัดเชิงตัวเลข เช่นพื้นที่ใช้งาน ความต้องการที่ได้รับการตอบ จำนวนบริการ หรือสถานะกิจการ ยังเป็นข้อเสนอ ต้องกำหนดว่าข้อมูลมาจากไหนและผู้เล่นมีผลอย่างไร ไม่รีบรวมทุกอย่างเป็นคะแนนดาวเดียว

ผลโลก ผลประเมินทักษะ และหลักฐานพอร์ตเป็นคนละข้อมูล ความรุ่งเรืองไม่ยืนยัน mastery และการเลือกเส้นทางต่างกันไม่ทำให้ผู้เล่นเสียสิทธิ์เรียนพื้นฐาน

## 8. GUI และบทสอนที่ต้องออกแบบใหม่

หน้าหมู่บ้านเสนอคำสั่งหลักเพียง **แผนที่ / คำขอ / จัดพื้นที่** พร้อมเงิน ตั้งค่า เต็มจอ และความช่วยที่เข้าถึงได้ แสดงงานปัจจุบันสั้น ๆ รายละเอียดเปิดเมื่อเลือกคนหรือแปลง

ออกแบบการวางแผนเป็นช่วงพื้นที่ → วัสดุ/สินค้า → ตัดสินใจ สรุปค่าที่ใช้ร่วมกันให้เห็นและกลับแก้ได้ร่างไม่หาย ไม่ทำเป็นฟอร์มยาวทุกเรื่องรวมกัน

สอนตรงวัตถุ/ปุ่มที่กำลังใช้: ชี้เป้าหมาย บอกสั้น ให้ลอง แล้วเห็นผล ไม่ใช้การ์ดยาวมุมจอเป็นเครื่องมือหลัก ผู้รู้แล้วข้ามได้ ผู้ติดเรียกดูซ้ำได้ ไม่ถือว่ากดตามครบแปลว่าเข้าใจ

ข้อผิดพลาดต้องมีทางไปต่อ เช่น “พื้นที่เก็บไม่พอ” → ดูผัง/ปรับจำนวน หรือ “เงินขาด” → เปรียบเทียบ/แก้รายการ ข้อความและเกณฑ์กู้ผิดต้องออกแบบก่อนโค้ด

ข้อความปรับขนาดได้ ลดการเคลื่อนไหวได้ ไม่ใช้สีหรือเสียงเพียงอย่างเดียวในการแจ้งผล และไม่ฝังสูตร/ราคาลงภาพ

## 9. การเรียน การประเมิน และพอร์ต

ยังยึดการสอน: ต้องหาอะไร/ทำไม → ข้อมูลและหน่วย → หลักการ → คำนวณ/ตรวจ → ใช้ตัดสินใจ เปิดบทตรงปัญหาแล้วกลับงานเดิมได้

ฝึกกับโครงการได้หลายครั้ง ส่วนการประเมินต้องมีข้อมูล/งานใหม่และเหตุผล เครื่องมือ/ความช่วยที่ใช้บันทึกตามจริง ตัวเลขที่ตรวจได้แยกจากเหตุผลที่ยังรอตรวจ ไม่ปลดสิทธิ์ความรู้เพียงเพราะกิจการรุ่งเรือง

พอร์ตเสนอเก็บคำขอ/เป้าหมาย แผนแรก–แก้ ผลโครงการ เหตุผลและหลักฐานพร้อมเงื่อนไขการช่วย ยังไม่ออกแบบช่องข้อมูลและเกณฑ์ทั้งหมด; ต้องทำหลังวงจรเล่นและโจทย์แรกชัด

ขยายวิชาอื่นผ่านกิจกรรม/ทักษะ/บท/หลักฐาน แยกเนื้อหาออกจากโลกและเศรษฐกิจ ไม่ผลิตหลักสูตรวิชาอื่นในรอบสรุปนี้

## 10. ภาพและเครื่องมือ

ภาพสร้างภายนอกตามพร็อมป์ที่จะเขียนจากแบบใหม่ ภาพคอมมิชเดิม33ไฟล์เก็บไว้เพื่อทบทวน ไม่ถือว่าใช้ได้ครบหรืออนุมัติแล้ว ดู [สถานะภาพ](ART_STATUS.md)

ต้องเตรียมฉากหลังร้านและภาพNPCสำหรับหน้าร้านเป็นงานใหม่ ไม่ใช้สเปกอาคารหลายมุมเดิมต่อโดยอัตโนมัติ ไม่มีตัวละครผู้เล่นเดิน จึงไม่ผลิตเฟรมเดินผู้เล่น ภาพ NPC และฉากหลังยังทบทวนภายหลัง

แนวทางเว็บเกมยังเป็นทิศทางที่คุยไว้ แต่ยังไม่เลือก/ติดตั้ง scaffold ใหม่หรืออ้างว่าเครื่องมือเก่าต้องใช้ทุกอย่าง บัญชีผู้เล่น ออนไลน์หลายคน บริการเสียเงิน และการเผยแพร่ไม่อยู่ในรอบนี้

## 11. ลำดับออกแบบต่อก่อนเริ่มโค้ด

ใช้ [ฐานการเรียนรู้และการเตรียมสอบ](EDUCATION_FOUNDATION.md) เป็นลำดับหลัก: ตรวจแหล่งข้อสอบ → วิเคราะห์ทักษะและหลักสูตร → วินิจฉัยพื้นฐาน → บทสอน/ฝึก/ประเมิน → ทดลองความเข้าใจ แล้วจึงออกแบบคำขอ NPC ระบบที่ดิน/เงิน GUI และภาพให้ตรงกับการเรียน ไม่เริ่มจากเศรษฐกิจหรือเควสเพื่อบังคับเนื้อหาให้ลงเกม

ยังไม่มีโค้ดฉบับใหม่ ต้องรอผู้ใช้สั่งเริ่มโค้ดโดยชัดเจน
